# Agent instructions: bsp-dev-c

This is the agent instruction file of this repository. It is excluded from source
archives (`export-ignore`).

## Overview

STM32F407IGHx (RoboMaster development board C) BSP built on LibXR and FreeRTOS. One
firmware project builds several robots; each robot is an XRobot application
configuration (product). Toolchain: XRobot 1.0 (`xrobot` CLI) and the LibXR code
generator 6.0 (`libxr` command). Docs: <https://xrobot.work/docs/proj_man>.

## Layout

| Path | Notes |
| --- | --- |
| `Core/` | CubeMX-generated init; edit only inside `/* USER CODE BEGIN */` / `/* USER CODE END */` |
| `Drivers/`, `Middlewares/ST/`, `Middlewares/Third_Party/FreeRTOS/` | Vendor code, read-only (see `NOTICE`) |
| `Middlewares/Third_Party/LibXR` | LibXR submodule (has its own `AGENTS.md`) |
| `Modules/modules.yaml` | Requested Modules and the `xrobot:` tool pin |
| `Modules/sources.yaml` | Module catalogs |
| `xrobot.lock` | Exact Module commits; change it only through `xrobot setup` |
| `Modules/<owner>/<Repo>/` | Module checkouts (separate Git repos, not tracked here) |
| `User/app_main.cpp` | Entry, generated by `libxr gen --xrobot`; hand-written code only inside `/* User Code Begin N */ ... End N */` |
| `User/libxr_config.yaml` | Peripheral buffer/queue settings, USB CDCs, database and the `generator:` pin |
| `User/xrobot.yaml`, `User/RobotConfig/*.yaml` | Application configurations (products) |
| `cmake/` | Toolchain files (as CubeMX wrote them) and `LibXR.CMake` (`XROBOT_MODULES_DIR`, `LIBXR_OPT_DEBUG`, `LIBXR_OPT_RELEASE`) |
| `tools/format_code.sh` | clang-format 21.1.8 over `Modules/` |

Generated, never edited or committed: `User/xrobot_main.hpp`, `Modules/CMakeLists.txt`.
Generated and committed (CI checks them): `User/app_main.cpp`, `User/app_main.h`,
`User/flash_map.hpp`, `User/libxr_config.yaml`.

## Commands

```bash
git submodule update --init --recursive
pip install xrobot==1.0.0 libxr==6.0.0      # match xrobot: and generator:
xrobot setup                                # fetch locked Modules, check every config, generate
xrobot gen -c User/RobotConfig/hero.yaml    # select a product
cmake --preset debug && cmake --build --preset debug
xrobot format --check                       # config layout (CI)
tools/format_code.sh --check                # C++ formatting of Modules/
```

The presets use `cmake/starm-clang.cmake` (picolibc) and need `starm-clang` on `PATH`;
`GCC_TOOLCHAIN_ROOT`/`CLANG_GCC_CMSIS_COMPILER` matter only for `STARM_HYBRID`.
`tools/build.sh -c <config> -p <preset>` runs formatting, `xrobot gen` and the cube-cmake build in one go.

After changing `DevC.ioc` and regenerating with CubeMX, the BSP objects are regenerated
with the same two commands CI runs (`libxr stm32 setup` is the one-time command that adds
LibXR to a CubeMX project):

```bash
libxr parse -d . -o .config.yaml
libxr gen -i .config.yaml -o User/app_main.cpp --xrobot --libxr-config User/libxr_config.yaml
```

## Execution flow

```
Reset_Handler -> main(): HAL_Init, SystemClock_Config, MX_*_Init, osKernelStart
  -> StartDefaultTask -> app_main() (User/app_main.cpp)
     -> construct STM32 peripheral objects, terminal, database
     -> XR_REGISTER(name, Type) for each object a config may use
     -> XROBOT_MAIN() -> XRobotMain (User/xrobot_main.hpp)
        -> construct Module instances (function-local statics, config order)
        -> loop: each instance's OnMonitor() in config order, sleep monitor_sleep_ms
```

Hardware is referenced by the C++ object name registered with `XR_REGISTER`.

## Application configurations

```yaml
modules:
  - module: QDU-Robomaster/RMMotor
    id: motor_yaw
    args:
      - can_bus: can2               # an XR_REGISTER name or an earlier instance id
      - param:                      # struct from a Module header: all fields, in order
          model: RMMotor::Model::MOTOR_GM6020
          reverse: false
          feedback_id: 522
settings:
  monitor_sleep_ms: 1000
```

- Values are C++ text; a string literal is a double-quoted YAML value (`"chassis_cmd"`).
  `null`/empty means "not filled in"; use `nullptr` for a null pointer.
- `args` names every parameter of one public constructor, in order.
- Instances may refer only to earlier instances (`id`, or `&id` for a pointer).
- Edit with `xrobot instance ...` or by hand; run `xrobot format` afterwards and
  `xrobot sync` after a Module adds or removes fields.
- Compiler errors in generated code point to the YAML line (`#line`).
- `xrobot describe` prints the registrations, constructors and diagnostics as JSON.

## Module work

- A Module is a plain C++ class `Repo` in `Repo.hpp`; its public constructor is the
  interface (dependencies as references/pointers without defaults first, then
  defaulted values). The header holds `MODULE MANIFEST V2` with
  `module_description`, `depends` and optionally `standalone`.
- Develop inside `Modules/<owner>/<Repo>/` and keep the changes uncommitted while
  iterating; `xrobot setup` refuses to move a Module with local changes or
  unpushed commits. Push to a branch of the Module repo, then run
  `xrobot setup --update <owner>/<Repo>` here.
- Module changes belong in the Module's own repository and PR, not in this repo.

## Branches and CI

- `dev` receives changes; `master` is updated only by PRs from `dev`.
- CI (`.github/workflows/xrobot_stm32.yml` calls the shared workflow
  `bsp-stm32-ci.yml` of the XRobot repository with the project name and the config
  list; container `ghcr.io/xrobot-org/docker-image-stm32:main`): installs the pinned
  tools, regenerates and diffs the BSP objects, rejects text files stored with CRLF,
  runs `xrobot format --check` and
  `xrobot setup --frozen --context-ref <built ref> --release-ref <target ref>`,
  then builds the default config and every `User/RobotConfig/*.yaml` with `-Werror`.
- Release gate: targeting `dev` requires locked Module commits on the Modules'
  `dev`; `master` or a tag requires them on the Modules' `master`.

## Conventions

Naming (enforced by `.clangd` / clang-tidy):
- variables and globals `lower_case`; class members `lower_case_`
- classes, structs, enums `CamelCase`; methods `CamelCase`; free functions `lower_case`
- constants (`const`/`constexpr`, any scope), enum constants and macros `UPPER_CASE`
- Module headers `PascalCase.hpp`; configs `snake_case.yaml`

Formatting: `.clang-format` is the LibXR style (Google-based, 90 columns, Allman braces,
`IncludeBlocks: Regroup`), and the generated `User/` files already follow it. clang-format
21.1.8 via `tools/format_code.sh`; scope is `Modules/` only.

Build: C11 and C++20, `-Werror`, Cortex-M4F, `-fno-rtti -fno-exceptions`,
`_printf_float` linked. The optimization levels are `LIBXR_OPT_DEBUG` (`-Og`) and
`LIBXR_OPT_RELEASE` (`-O3`) in `cmake/LibXR.CMake`; the toolchain files stay as CubeMX
wrote them.

LibXR allocates during initialization and keeps the allocations for the lifetime of the
program; allocations are not paired with frees.

## Do not

- edit `Core/` outside USER CODE blocks, or anything under `Drivers/` and
  `Middlewares/` (vendor code; override weak HAL callbacks in `User/` or
  `Core/Src/stm32f4xx_hal_msp.c`)
- use Legacy HAL APIs (`Drivers/STM32F4xx_HAL_Driver/Inc/Legacy/`)
- edit generated files (`User/xrobot_main.hpp`, `User/flash_map.hpp`,
  `Modules/CMakeLists.txt`, generated parts of `User/app_main.cpp`)
- edit `xrobot.lock` by hand
- add `#pragma` diagnostic suppressions to application code
- commit `build/` or mix regenerated files with functional changes in one commit

Commits: short imperative subject, one logical change per commit.
